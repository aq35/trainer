# Git を調べるコツ — AI と Git 自身を、両方使う

<div class="lead">
分からないことを AI に聞くのは、正しい使い方です。<br>
ただし AI は、<b>あなたのパソコンの中を見ていません</b>。見えていないまま、それらしく答えます。<br>
この読み物は、<b>AI の答えを「理解」に変えるための型</b>です。
</div>

## いちばん大事な1行

> **事実は Git に聞く。意味は AI に聞く。答えは Git で確かめる。**

| 何を知りたいか | 聞く相手 | なぜ |
| --- | --- | --- |
| いま、どのブランチにいるか・何を変えたか | **Git**（`git status`） | Git は手元の事実しか言わない。AI は推測しかできない |
| そのメッセージは、どういう意味か | **AI** | 英語と専門用語を、あなたの言葉に直すのは AI が得意 |
| AI の答えは合っているか | **Git**（試す・`--help`・公式の説明） | 確かめるまでは「仮説」のまま |

この順番を守るだけで、**AI が自信たっぷりに間違えても、事故になりません**。

## コツ1: 聞く前に「いまの状態」を集める

AI に「push できません」とだけ送ると、**よくある原因を10個**並べて返してきます。あなたの原因がどれかは分かりません。
先に、Git に状態を言わせてから、**それを丸ごと貼ります**。

```
git status
git log --oneline --graph -n 5
git branch -vv
```

| コマンド | 分かること |
| --- | --- |
| `git status` | いまのブランチ、変更したファイル、コミットしていない変更 |
| `git log --oneline --graph -n 5` | 直近5件のコミットと、枝分かれの形 |
| `git branch -vv` | 手元のブランチが、GitHub のどのブランチとつながっているか・何件ずれているか |

<div class="note">
<b>エラーは、全文を貼ってください。</b>「なんかエラーが出た」や、最後の1行だけでは、原因が絞れません。<b>最初の1行に答えが書いてあることが多い</b>です。
</div>

送る文章の型です。そのまま使えます。

```
Git を勉強中の初心者です。次のことをしようとして、うまくいきません。

【やりたいこと】
（例: 作ったブランチを GitHub に上げたい）

【打ったコマンド】
（ここに貼る）

【出てきたメッセージ（全文）】
（ここに貼る）

【いまの状態】
git status の結果:
（ここに貼る）
git log --oneline --graph -n 5 の結果:
（ここに貼る）

次にやることを1つだけ、理由と一緒に教えてください。
消えてしまう変更がある操作なら、先にそう言ってください。
```

## コツ2: 打つ前に、3つだけ聞く

AI が「このコマンドを打ってください」と言ったら、**打つ前に**この3つを聞きます。

```
さっきのコマンドについて、3つ教えてください。
1. 作業ディレクトリ・ステージングエリア・リポジトリのうち、どれが変わりますか
2. 消えて、取り戻せなくなるものはありますか
3. 打ったあと「やっぱりやめたい」ときは、どう戻しますか
```

**2番の答えが「あります」なら、止まってください。** 先に `git stash` や commit で逃がしてから打ちます。
3番に答えられないコマンドは、**まだ打つ段階ではありません**。

## コツ3: 止まるべき言葉を覚えておく

AI が次のコマンドを出してきたら、**意味が分かるまで打たないでください**。どれも「取り戻せない」か「他人に影響する」ものです。

| コマンド | 何が起きるか | 代わりに聞くこと |
| --- | --- | --- |
| `git reset --hard` | ステージングエリアと作業ディレクトリの、コミットしていない変更が**消える** | 「変更を残したまま戻す方法は？」 |
| `git clean -fd` | **追跡されていない**ファイルとフォルダが**消える** | 先に `git clean -n`（消えるものの一覧だけ出す）を打つ |
| `git checkout -- .` / `git restore .` | 作業ディレクトリの、コミットしていない変更が**消える** | 「消えるのはどのファイル？」 |
| `git push --force` | GitHub 上の**他人のコミットを上書き**しうる | 「チームで使っているブランチでも大丈夫？」 |
| `git rebase` | コミットを**作り直す**。プッシュ済みだと他人とずれる | 「merge ではだめな理由は？」 |

根拠（Git リファレンス・英語）: [git reset](https://git-scm.com/docs/git-reset) ／ [git clean](https://git-scm.com/docs/git-clean) ／ [git restore](https://git-scm.com/docs/git-restore) ／ [git push](https://git-scm.com/docs/git-push)（`--force`）／ [git rebase](https://git-scm.com/docs/git-rebase)

<div class="checkpoint">
<strong>迷ったら、先に保険をかけます。</strong><br>
<code>git stash</code> は、コミットしていない変更を<b>いったん片付けて、別の場所に保存</b>します（<code>git stash pop</code> で戻せます）。<code>git switch -c backup</code> は、いまのコミットに <b>backup という目印（ブランチ）</b>を付けます。どちらも、変更を捨てるコマンドではありません（根拠: <a href="https://git-scm.com/docs/git-stash" target="_blank" rel="noopener">git stash</a>・<a href="https://git-scm.com/docs/git-switch" target="_blank" rel="noopener">git switch</a>）。
</div>

## コツ4: AI の答えを、Git で確かめる

AI の答えは、**確かめるまでは仮説**です。確かめ方は4つあります。

### ① 空打ちする（試すだけで、何も変えない）

| コマンド | 何をするか |
| --- | --- |
| `git clean -n` | 消えるファイルの一覧だけ出す |
| `git add -n .` | ステージに載るファイルの一覧だけ出す |
| `git push --dry-run` | 送る内容の確認だけする |

### ② 使い捨てのフォルダで試す

本物のリポジトリで試さないでください。**1分で作れる練習場**があります。

```
mkdir git-lab
cd git-lab
git init
echo 1 > a.txt
git add a.txt
git commit -m "1回目"
```

ここなら、何を壊しても**フォルダごと消せば元通り**です。AI に「このコマンドはこう動く」と言われたら、**ここで打って、本当にそうなるか**見てください。

### ③ Git 自身の説明を読む

```
git help status
git status -h
```

`-h` は短い一覧、`git help` は詳しい説明です。**AI の説明と食い違ったら、Git の説明が正しい**と考えてください。

### ④ 公式の説明に当たる

- [Git のリファレンス](https://git-scm.com/docs) — 全コマンドの正式な説明（英語）
- [Pro Git（日本語版）](https://git-scm.com/book/ja/v2) — Git の公式の解説書。無料で全部読めます

AI に「**その説明は、公式のどこに書いてありますか**」と聞くのも有効です。答えられない、またはリンク先に書いていないなら、その説明は疑ってください。

<div class="note">
<b>バージョンの違いに注意。</b><code>git switch</code> と <code>git restore</code> は、Git 2.23（2019年）で増えたコマンドです。古い記事や AI の答えでは、同じことを <code>git checkout</code> で書いています。<b>どちらも正しい</b>ので、混乱したら <code>git --version</code> を確かめてから聞いてください。
</div>

## コツ5: 理解を深める聞き方

動かせたあとに、**もう1問だけ**聞くと、次に同じことで詰まらなくなります。

### たとえで聞いて、たとえの限界も聞く

```
「ステージ」を、身近なものにたとえて説明してください。
そのあと、そのたとえが当てはまらないところも教えてください。
```

たとえだけだと、**たとえの外側で間違えます**。限界まで聞いて、はじめて使える理解になります。

### 自分の言葉で説明して、直してもらう

```
私の理解を書きます。間違っているところだけ、理由と一緒に直してください。
合っているところは「合っています」だけで構いません。

（ここに、自分の言葉で説明を書く。例:
 ブランチは、フォルダを丸ごとコピーしたものだと思っています）
```

**いちばん効く聞き方です。** 分かったつもりの穴が、ここで見つかります。
（ちなみに上の例は間違いです。ブランチは**コミットを指している目印（ポインタ）**で、コピーではありません（[Pro Git 3.1「ブランチとは」](https://git-scm.com/book/ja/v2/Git-のブランチ機能-ブランチとは.html)）。AI がそう直してくれるか、試してみてください）

### 中身を見に行く

Git のコミットは、手元の `.git` フォルダの中に**本当に入っています**。AI に説明させたら、実物も見てください。

```
git cat-file -p HEAD
```

いまのコミットの中身が出ます。「誰が・いつ・どのコミットの次に・何というメッセージで」が、**ただの文字として**書いてあるのが見えます。
出てきたものを AI に貼って、「**1行ずつ、何が書いてあるか教えてください**」と聞いてみてください。

### 図にしてもらう

```
次の git log --graph の結果を、枝分かれが分かるように説明してください。
どのブランチがどこから分かれて、どこで合流したかを教えてください。

（git log --oneline --graph --all -n 15 の結果を貼る）
```

## コツ6: 貼ってはいけないもの

AI に送った文章は、**あなたの手元から外に出ます**。次のものは消してから貼ってください。

- パスワード、アクセストークン（`ghp_` で始まる文字列など）
- `.env` など、鍵や設定が書いてあるファイルの中身
- `git remote -v` の結果に、**URL の中にトークンが入っている**ことがあります（`https://ユーザー名:トークン@github.com/...`）
- 会社のリポジトリ名・顧客名（仕事で使うときは、**貼ってよいかを先に確認**）

<div class="qa">
<div class="q">間違えて、トークンを貼ってしまいました</div>
<div class="a"><b>すぐに、そのトークンを無効にしてください</b>（GitHub の Settings → Developer settings から消せます）。<b>消したつもりの文章は、取り消せないと考えてください</b>。新しいトークンを作り直せば、元に戻れます。</div>
</div>

## まとめ: 1枚にすると

| 場面 | やること |
| --- | --- |
| 詰まった | `git status` などで**状態を集めて**から、全文を貼って聞く |
| コマンドを勧められた | **何が変わる・何が消える・どう戻す**、を先に聞く |
| 危ない言葉が出た | 止まる。保険（`stash` / 目印のブランチ）をかける |
| 答えが返ってきた | **空打ち・使い捨てフォルダ・`git help`・公式**で確かめる |
| 動いた | **自分の言葉で説明して、直してもらう**。1問だけでいい |
