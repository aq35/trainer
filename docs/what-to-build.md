# AIに何を作ってもらうか — 使い捨ての仕事と、残る道具

<div class="lead">
ここまでで、AIに「直して」「作って」と頼むことには慣れました。<br>
次は<b>頼む中身</b>の話です。ここで差がつきます。<br>
<b>同じ仕事を毎回頼む人</b>と、<b>その仕事が要らなくなる道具を作らせる人</b>。<br>
半年後、この2人はまったく別の場所にいます。作業はありません。読むだけです。
</div>

## 同じことを、何回頼みましたか

練習リポジトリで、こんなことをしていませんでしたか。

> 「このコード、ちゃんと動いてる？」
> 「さっき直したところ、壊れてないか見て」
> 「タスクのデータをもう10件ぶん作って」
> 「今どのタスクが期限切れか数えて」

**全部、毎回頼んでいます。** そしてAIは毎回、まじめに答えます。答えは合っているかもしれません。
でも、**次の日も、その次の日も、同じことを頼むことになります。**

<div class="checkpoint">
<strong>ここが分かれ道です。</strong><br>
「確かめて」と<b>毎回頼む</b>のか、「確かめる仕組みを作って」と<b>1回頼む</b>のか。
</div>

## 使い捨ての仕事 vs 残る道具

同じ「AIに頼む」でも、返ってくるものの寿命がまったく違います。

| 頼み方 | 返ってくるもの | 寿命 |
| --- | --- | --- |
| 「この関数、合ってる？」 | **その場の答え** | **その場かぎり** |
| 「この関数のテストを書いて」 | **テストのコード** | **ずっと残り、毎回自動で走る** |
| 「画面の動きを確認して」 | 「たぶん大丈夫です」 | その場かぎり |
| 「画面の動きを確認する E2E テストを書いて」 | **確認を自動でやるコード** | **ずっと残る** |
| 「テスト用のデータを10件作って」 | 10件のデータ | 1回きり |
| 「テスト用のデータを好きな件数作るスクリプトを書いて」 | **道具** | **ずっと残る** |

<div class="qa">
<div class="q">でも、道具を作るほうが時間かかりますよね？</div>
<div class="a"><b>初回は、かかります。</b>2回目で並び、3回目から得をします。<b>そして道具は、あなたが寝ている間も働きます。</b>プルリクエストを出すたび、自動チェックが勝手に走っていたでしょう。あれです。誰も操作していません。</div>
</div>

## 何を作ってもらうと、いちばん効くのか

現場で効果が大きい順に4つ挙げます。**この4つを知っているだけで、頼み方が変わります。**

### ① 単体テスト —— いちばん最初に作るべき道具

**関数ひとつひとつが、正しく動くかを確かめるコード**です。練習リポジトリのチケット#5で、あなたはこれを自分の手で書きました。

- **効くタイミングは、書いた瞬間ではありません。** 半年後、別の人が別の場所を直したときです
- **リファクタリング（書き直し）の許可証**になります。チケット#6で体験したとおりです
- **AIに書かせるのがいちばん向いている領域**でもあります。ただし「実装は変えないで」を必ず添えること

<div class="note">
<b>テストは「仕様書」でもあります。</b> 「この関数は、空の配列を渡すと 0 を返す」——テストを読めば、その関数が何をするものか分かります。<b>しかも、説明文と違って古くなりません。</b> 嘘をつけば赤くなるからです。
</div>

### ② E2E テスト —— 画面を人の代わりに触ってもらう

E2E は End to End（端から端まで）の略です。**ブラウザを自動で開き、実際にクリックして、表示を確かめるテスト**です。

> 検索欄に「買い物」と入力する → 一覧が1件になる → その1件のタイトルが「買い物に行く」である

これを人間が毎回やると、**3分かかって、しかも飽きます。飽きると、やらなくなります。**
機械にやらせれば、**20秒で、何度でも、飽きずに**やります。

<div class="qa">
<div class="q">単体テストがあるのに、なぜ必要なんですか？</div>
<div class="a"><b>部品が全部正しくても、組み立てが間違っていることがあるからです。</b>関数は全部緑なのに、画面には何も表示されない——ボタンをつなぎ忘れただけ、というのはよくあります。<b>単体テストは部品を、E2Eは組み立てを見ています。</b></div>
</div>

<div class="note">
<b>研修では作りません。</b>準備に手間がかかるので、いまは「そういうものがある」と知っていれば十分です。案件で「E2E落ちてるよ」と言われたときに、<b>何の話か分かる</b>——それが今日のゴールです。
</div>

### ③ 開発用のデータと、動く置き場所（DB）

「テストしたいけど、データが3件しかない」——これは全員がぶつかります。

**AIに頼めば、置き場所ごと用意してくれます。**

> 「開発中に使うタスクのデータを、200件作るスクリプトを書いてください。
> 期限切れ・今日が期限・期限なしが、ほどよく混ざるようにしてください」

さらに進めるなら、こう頼めます。

> 「いまは JSON ファイルを読んでいますが、データベース（SQLite）に置き換えたいです。
> 手順を先に説明してから、進めてください」

<div class="checkpoint">
<strong>「データベースは、まだ自分には早い」と思っていませんか。</strong><br>
<b>それは逆です。</b>AIと一緒なら、<b>入れる → 動かす → 壊す → 直す</b>を今日できます。本を1冊読んでから触るより、<b>動いているものを触りながら覚えるほうが、ずっと速い。</b>ただし1つだけ約束してください——<b>手順を説明させてから進めること。</b>分からないまま動いたものは、壊れたときに直せません。
</div>

### ④ 集計・分析のスクリプト

**データを見て、判断するためのコード**です。

> 「期限切れのタスクを、タグごとに集計して表にするスクリプトを書いてください」

地味に見えますが、**これができる人は強い**です。理由は単純で、**「なんとなくこう思う」ではなく「数字ではこうなっている」と言えるから**です。

<div class="qa">
<div class="q">データアナリストを目指しているのですが、関係ありますか？</div>
<div class="a"><b>ど真ん中です。</b>分析の仕事の大半は、集計する前の「データを取ってきて、形をそろえる」部分です。そしてそこは、<b>ここまでやってきたこと（ファイルを読む・関数を書く・テストで確かめる）とまったく同じ</b>です。<a href="#/path">どこへ行く？ 職種と土台</a>も見てみてください。</div>
</div>

## 「開発体験を上げる」とは、こういうこと

上の4つには、共通点があります。**どれも、機能そのものではありません。**
お客さんの画面には1ピクセルも出てきません。それでも作る価値があるのは、**作る人の速さと安心が変わるから**です。

これを **開発体験（Developer Experience）** と呼びます。

| よくある症状 | 作れば消える道具 |
| --- | --- |
| 直すたびに、手で全部クリックして確認している | **テスト**（単体・E2E） |
| 環境を作るのに、毎回半日かかる | **セットアップの手順を1コマンドにまとめたもの** |
| 毎回「今どうなってる？」と聞いて回っている | **集計スクリプト／ダッシュボード** |
| データが足りなくて、まともに試せない | **データを作るスクリプト／開発用DB** |
| 同じ説明を、毎回AIにしている | **`CLAUDE.md` に前提を書く** |

<div class="trivia">
<div class="ct">気づきましたか</div>
最後の行は、<b>この研修ですでにやっています。</b>「自分のテーマで回す」で <code>CLAUDE.md</code> を書きましたよね。あれも立派な「開発体験を上げる道具」です。<b>毎回する説明を、1回で済ませた</b>——やったことの意味が、いま分かったはずです。
</div>

## そして、これがいちばん大事な話

<div class="lead">
<b>作った道具は、チームの皆に共有してください。</b>
</div>

自分だけが速くなっても、**チームは速くなりません。** そして仕事は、チームで進みます。

- テストの書き方を工夫したら、**書き方をチャットに1行流す**
- 便利なスクリプトを作ったら、**リポジトリに入れて、READMEに使い方を3行書く**
- AIへの頼み方でうまくいったものがあったら、**そのまま貼って共有する**
- 詰まって抜けた方法は、**次に詰まる人のために書き残す**

<div class="qa">
<div class="q">共有すると、自分の価値が下がりませんか？</div>
<div class="a"><b>逆です。</b>「あの人に聞くと、皆が速くなる」という評判ほど強いものはありません。情報を抱えている人は、<b>その情報が古くなった瞬間に価値を失います</b>。共有する人は、<b>共有し続けるかぎり価値が上がり続けます</b>。<br>それに、実際にやってみると分かりますが——<b>説明しようとすると、自分の理解のほうが深まります。</b></div>
</div>

<div class="checkpoint">
<strong>皆が幸せになる道を考えられるエンジニアが、最終的にはいちばん強い。</strong><br>
これは精神論ではありません。<b>チームの速さが、その人の成果の上限を決めるから</b>です。<br>
一人で速い人は、一人ぶんしか進みません。まわりを速くできる人は、<b>チームの人数ぶん</b>進みます。<br>
そして、そういう人のところに、次の仕事が来ます。
</div>

## 明日からできること

大きなことをしなくて構いません。**次にAIに何かを頼むとき、こう自問してください。**

> **これ、来週も同じことを頼むだろうか？**

**「頼む」と思ったら、その場の答えではなく、道具を作らせてください。**

<div class="note">
そして道具ができたら、<b>誰か1人に見せてください。</b>チームでも、一緒に学んでいる人でも、この教材の <a href="https://github.com/aq35/trainer/discussions" target="_blank" rel="noopener">Discussions</a> でも構いません。<b>見せた瞬間から、それはあなた1人の道具ではなくなります。</b>
</div>

## まとめ

- AIへの頼みごとには、**使い捨ての仕事**と**ずっと残る道具**がある
- 効くのは **① 単体テスト ② E2E ③ 開発用のデータ・DB ④ 集計スクリプト**
- **DBも、AIに頼めば今日から触れる。** ただし**手順を説明させてから**進めること
- 機能ではないものを作るのは、**作る人の速さと安心が変わるから**
- そして——**作った道具は、必ず共有する**
