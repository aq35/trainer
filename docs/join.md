# 案件に参画する — 準備と、最初の2週間

<div class="lead">
研修が終わっても、案件には自動では入れません。<b>「この人は何ができるのか」が伝わって、はじめて話が始まります。</b><br>
うれしいことに、<b>その材料はもう全部あなたのGitHubにあります</b>。あとは、伝わる形にするだけです。
</div>

## 1. 自分の「証拠」を集める

未経験者がいちばん困るのが、**「できます」を証明できないこと**です。あなたには証拠があります。

<div class="note">
下のURLを、<b>いますぐメモ帳に貼り出してください。</b>これがあなたの職務経歴書のかわりになります。
</div>

| 集めるもの | どこにあるか |
| --- | --- |
| **公開したページ** | `https://あなたの名前.github.io/my-page/` |
| **自分のテーマの成果物** | GitHubの `my-theme` リポジトリ（非公開なら、見せるときだけ公開に） |
| **他人のコードを直した記録** | `trainer-practice` の **Pull requests** タブ（4件のPRが並んでいるはず） |
| **コミットの履歴** | 各リポジトリの Commits |
| **できること・弱いところ** | [🎓 最終チェック](graduation.md)のチェック結果 |

<div class="checkpoint">
<strong>「4つのチケットを、PRを出して直した記録」は、想像以上に強い材料です。</strong> 未経験者の応募でこれが出てくることは、まずありません。<b>言葉ではなく履歴で示せる</b>のが、この研修をやった人の強みです。
</div>

## 2. 自己紹介（スキルシート）を作る

材料が集まったら、AIに整形してもらいます。**盛らないこと**が最重要です。

<div class="note">
<b>できないことを書けるかどうかで、参画後がまったく変わります。</b> 「できます」と言って入って、できなかった場合、失うのは信頼です。<b>正直に書いた人のほうが、結果的に良い扱いを受けます。</b>
</div>

下の文章をコピーして、GitHubのURLを差し替えてAIに送ってください。

```
私は未経験からエンジニアを目指していて、これから開発案件に参画します。
案件の担当者に渡す自己紹介（スキルシート）を作りたいので、手伝ってください。

# 私がやったこと
- 研修で、git / GitHub / HTML / JavaScript / 開発者ツール / AIとの組み方を一通り学んだ
- 他人が書いたリポジトリを clone し、チケット4件をPRで直した
  （404の調査、エラーが出ない不具合の切り分け、あいまいな依頼の要件確認、コンフリクト解決）
- 自分でテーマを決めたものを1週間ぶん作り、GitHubに毎日記録した
- 作ったページを GitHub Pages で公開した

# 証拠になるURL
- 公開ページ: （ここにURL）
- 練習リポジトリのPR一覧: （ここにURL）
- 自分のテーマのリポジトリ: （ここにURL）

# お願い
1. A4半分くらいの分量で、自己紹介を作ってください
2. **できることと、できないことを両方**書いてください。盛らないでください
3. 未経験であることは隠さず、そのうえで「何ができるか」が伝わる書き方にしてください
4. 専門用語を使いすぎないでください。読むのは技術者とは限りません
5. 私が書き足すべき項目があれば、質問してください
```

<details>
<summary>「できないこと」には、何を書けばいい？</summary>

正直に書いて構いません。むしろ**書いたほうが信頼されます**。例です。

- **業務でのコード経験はありません**（研修と個人の練習のみです）
- データベースは扱ったことがありません
- チームでの開発は未経験です（レビューを**受けた**経験は、自動チェックとAIのみ）
- 分からないことは、15分で人に聞くようにしています

最後の1行のような**「詰まったときにどう動くか」は、実は現場が一番知りたいこと**です。技術より、こちらで判断されます。
</details>

## 3. 参画の準備ができたことを、担当者に伝える

準備ができたら、研修の担当者に知らせます。**完璧である必要はありません。**

<div id="joinbtn"></div>

<div class="note">
押すと、<b>いまの到達状況が文章になってコピー</b>されます（担当者が GitHub の窓口を用意している場合は、そちらが開きます）。<br>
成果物のURLと、自信が無いところを書き足して、<b>いつもの連絡手段でそのまま送ってください</b>。
</div>

## 4. 案件が決まったら —— 最初の2週間が山です

<div class="qa">
<div class="q">技術がついていけるか不安です</div>
<div class="a">最初の2週間で時間を溶かすのは、<b>技術ではありません。</b>「環境が動かない」「どこに何があるか分からない」「誰に聞けばいいか分からない」——この3つです。<b>全員が通ります。</b>あなたの能力の問題ではありません。</div>
</div>

### 初日にやること

- [ ] **環境を動かす**。まずここに集中する（動かないのが普通です。半日かかっても正常）
- [ ] **リポジトリを clone して、コードを開いてみる**（読めなくてよい。場所の把握だけ）
- [ ] **聞いてよい相手と、聞き方を確認する**（チャット？ 口頭？ 何分待つ？）
- [ ] **ルールを聞く** — ブランチ名、コミットの書き方、**AIを使ってよいか**
- [ ] **自分の役割と、最初のタスクを確認する**

<div class="note">
⚠️ <b>「AIを使ってよいか」は、初日に必ず確認してください。</b> チームごとにルールが違います。「他所ではOKだった」は理由になりません。<a href="ai.html" target="_blank" rel="noopener">AIと一緒に直す</a>で覚えたとおりです。
</div>

### 毎日やること

**日報を出してください。** 求められていなくても出す価値があります。1日3行で十分です。

```
【今日やったこと】
・〇〇の画面のボタンの不具合を調べた

【詰まっていること】
・ローカルでビルドが通らない（エラー: ...）。明日も続く場合は相談させてください

【明日やること】
・上記の続き。通ったら修正に入る
```

<div class="checkpoint">
<strong>これを出しているだけで、評価がまったく変わります。</strong> 未経験者にいちばん不足しているのは技術ではなく、<b>「いま何をしていて、どこで困っているか」が周りに見えないこと</b>だからです。見えていれば、周りは助けられます。
</div>

### 2週間目にやること

- [ ] **最初のPRを出す**（どんなに小さくてよい。文言修正でも構いません）
- [ ] **レビューの指摘に返信する**（「直しました」だけでなく、直した内容も一言）
- [ ] 分からないまま流していることを、**リストにして一度まとめて聞く**

<div class="note">
<b>指摘は、あなたへの評価ではありません。</b> コードに対する意見です。ベテランでも毎回指摘されます。<br>
逆に、<b>指摘に無言で対応するのはよくありません。</b>「読みました」「直しました」の一言があるだけで、印象は変わります。
</div>

## 5. 続かないと感じたら

<div class="qa">
<div class="q">周りに迷惑をかけている気がして、つらいです</div>
<div class="a"><b>最初の1か月は、全員が「戦力になっていない」状態です。</b>それは織り込まれています。<br>本当に問題なのは、<b>詰まっていることを黙っていること</b>です。1日黙ると1日ぶん、1週間黙ると1週間ぶん、周りは驚きます。<b>早く言うほど、迷惑は小さくなります。</b></div>
</div>

<div class="qa">
<div class="q">向いていないかもしれません</div>
<div class="a">1か月で判断しないでください。<b>「分からないことが分からない」期間は、誰にでもあります。</b><br>それでも苦しいときは、研修の担当者に連絡してください。<b>案件を変える、時期をずらす、という選択肢もあります。</b>やめる前に、一度相談してください。</div>
</div>
