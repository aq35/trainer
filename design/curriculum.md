# 教材の設計（作り直し・たたき台）

> 状態: **設計案**。まだ教材は書いていません。この文書で合意してから作ります。

## 1. 何を教えるか

**Git だけを教えます。** 黒い画面が初めての人が、**チームの開発で Git を任せても事故を起こさない状態**になるまで。

外すもの（今の教材から消す）:

- Git と関係のない学習: プログラミング入門、AI との開発、性能改善、グラフ、API、データベース、テスト、MCP、案件参画、学習計画
- 寄付の案内、「この教材は無料です」の説明（`about.md`、目次の注意書き、`config.js` の `coffee`）
- 逆算プランナー、参画の相談、参画準備のチェックリスト

残すもの（仕組み。中身ではない）:

- sunao で作った画面（1画面1操作のナビ、読み物、コマンド練習）とビルド・公開の仕組み
- ナビの型: **手順 → こうなれば成功です → できましたか？ → 次へ**、「うまくいきません」の3段構え、15分で声をかける
- 連絡先の設定（詰まったときの相談先）

## 2. ゴール（卒業したら、できること）

1. 変更を**意味のある単位**で記録し、あとから**理由まで**追える
2. 壊しても、**自分で元に戻せる**（どのコマンドが何を消すか、分かって打てる）
3. ブランチで作業し、**コンフリクトを落ち着いて解決**できる
4. GitHub で**プルリクエストを出し、レビューを受けて直し、レビューする側にも回れる**
5. チームの**ブランチ運用のルールを読んで、それに従える**
6. 事故（間違ったブランチで commit、秘密を push、push を拒否された）から**復旧の手順を選べる**

**測り方**: 最後の回で、練習用リポジトリに**用意された事故**を自分で直し、プルリクエストで提出する。自動チェックが通れば合格。点数は付けない。

## 3. 設計の原則

| 原則 | 具体的には |
| --- | --- |
| 1画面に1つだけ | 今と同じ。分岐や自由探索を置かない |
| **打つ前に読む、打った後に読む** | **全コマンドに**「この行は何をするか」と「いま何が起きたか」を付ける（今は 110 画面中 8 画面）。**ビルドで検査し、欠けていたら公開しない** |
| 先に壊して、戻す | 各回に「わざと壊して戻す」画面を必ず1つ入れる。**戻せると知ってから**、怖い操作を教える |
| 手元の状態を目で見せる | 「作業フォルダ／ステージ／記録」の3つの箱の図を、**毎回同じ絵で**出す。どの箱が変わったかだけ色を変える |
| 固定の題材で練習する | 練習用リポジトリに、**回ごとの出発点**をブランチで用意する。前の回で失敗しても、次の回は同じ場所から始められる |
| **AI は「調べる道具」として使う** | 手順は VS Code と Git だけで進められる。そのうえで、**各回の完了画面に「AI で深める」を1問**置き、理解を深めるのに AI を使う。聞き方の型は読み物「Git を調べるコツ」にまとめる |

## 4. 構成（全 16 回・4 部）

各回 8〜12 画面、1回 30〜60 分。**★ は「わざと壊して戻す」画面がある回**。

### 第1部 一人で記録する

| # | 回 | できるようになること | 主なコマンド |
| --- | --- | --- | --- |
| 1 | 道具をそろえる | ターミナルを開き、Git を入れ、名前を登録する | `git --version` `git config` |
| 2 | 最初の記録 | フォルダを記録の対象にし、1回記録する | `init` `status` `add` `commit` |
| 3 | 3つの箱 ★ | 作業フォルダ・ステージ・記録の違いが説明できる | `status` `add` `restore --staged` |
| 4 | 差分を読む | 何を変えたかを、記録する前に確かめる | `diff` `diff --staged` |
| 5 | 履歴をたどる | いつ・誰が・なぜ変えたかを探す | `log` `log --oneline` `show` |
| 6 | 戻す ★ | 目的に合った戻し方を選べる | `restore` `commit --amend` `revert` |
| 7 | 記録しないもの | 記録してはいけないものを外す | `.gitignore` `rm --cached` |

### 第2部 枝分かれ

| # | 回 | できるようになること | 主なコマンド |
| --- | --- | --- | --- |
| 8 | ブランチ ★ | 本線を汚さずに試す。ブランチはラベルだと分かる | `branch` `switch -c` `switch` |
| 9 | 合流する | 早送りと、合流の記録ができる場合の違い | `merge` `log --graph` |
| 10 | コンフリクト ★ | 衝突を読み、選び、仕切り直せる | `merge --abort` 記号の読み方 |

### 第3部 GitHub で人と組む

| # | 回 | できるようになること | 主なコマンド |
| --- | --- | --- | --- |
| 11 | GitHub に上げる | 手元の記録を送り、他人のものを持ってくる | `remote` `push` `clone` |
| 12 | 取り込む ★ | 他人の変更を取り込み、push を拒否されても直せる | `fetch` `pull` rejected の読み方 |
| 13 | プルリクエスト | 説明つきで出し、指摘を受けて直す | `push -u` PR・レビューへの返信 |
| 14 | レビューする側 | 差分を読み、伝わる指摘を書く | GitHub のレビュー画面 |

### 第4部 現場の運用

| # | 回 | できるようになること | 主なコマンド |
| --- | --- | --- | --- |
| 15 | ブランチ運用 | GitHub Flow と Git-Flow を読み、ルールに従える | `tag` 運用の図 |
| 16 | 事故から戻る ★（卒業課題） | よくある事故を自分で直して、PR で提出する | `stash` `reflog` `reset` `cherry-pick` |

**入れない（理由）**: `rebase`（卒業後に扱う。チームのルール次第で、未経験者が最初に触ると事故が多い）／ `submodule`・`worktree`・`bisect`（使う場面が案件に入ってからしか来ない）。**読み物で「ある」とだけ知らせる**。

## 4.5 AI で Git の理解を深める（全回を通す線）

**事実は Git に聞く。意味は AI に聞く。答えは Git で確かめる。** この順番を、全16回で繰り返し練習する。
型は読み物 [Git を調べるコツ](../content/read/git-research.md) にまとめてあり、各回からここへ戻る。

| 場所 | 何を置くか |
| --- | --- |
| 第1回の完了画面 | 「Git を調べるコツ」を読む（最初の1回だけ、読むことを勧める） |
| 各回の完了画面 | **AI で深める**: その回の概念について、コピーして使える質問を1つ。多くは「**自分の言葉で説明して、AI に直してもらう**」形にする |
| 「うまくいきません」の AI に聞く文章 | `git status` と `git log --oneline --graph -n 5` の結果を**貼る欄**を足す（状態を渡さないと、AI は推測しかできない） |
| ★ の回（わざと壊して戻す） | 「打つ前に3つ聞く」（何が変わる・何が消える・どう戻す）を**実際に AI に聞いてから**打つ画面を1つ入れる |
| 第6回・第16回 | 「止まるべき言葉」（`reset --hard` / `clean -fd` / `push --force` など）を、AI が勧めてきた想定で見分ける |
| 卒業課題 | 事故の直し方を AI に聞いてよい。ただし PR の説明に「**AI の答えを、どう確かめたか**」を書く（空打ち・使い捨てフォルダ・`git help` のどれか） |

**AI の答えをそのまま信じない練習**も入れる。第5回（履歴）で、わざと古い書き方（`git checkout` で戻す）の答えが返ってくる質問を用意し、`git --version` と `git help` で確かめさせる。

## 5. 読み物（寄り道・任意）

Git に関係するものだけ。各回の完了画面から1本だけ案内する。

- **Git を調べるコツ**（AI と Git 自身を両方使う。**書き済み**: `content/read/git-research.md`）
- なぜ Git が生まれたのか（今のものを流用）
- Git の中身: 記録はスナップショット、ブランチはラベル、`HEAD` は「いまここ」
- 消えるコマンド・消えないコマンドの表（`restore` `reset --hard` `clean` はどこを消すか）
- コマンド早見表（逆引き: 「〇〇したい → このコマンド」）
- 用語集（Git の言葉だけに絞る）

## 6. 練習用リポジトリ

`aq35/trainer-practice` を **Git 専用に作り直す**（今は Web アプリの修正チケットが中心）。

- `start/08-branch` のように、**回ごとの出発点**をブランチで置く
- 第3部は、**相手役の変更を GitHub Actions が自動で push する**（一人でも「他人と同時に触る」を体験できる）
- 卒業課題のチェックは Actions で機械的に行う（履歴に秘密が無い・main が壊れていない・PR に説明がある）
