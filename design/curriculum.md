# 教材の設計（作り直し）

> 状態: **第2版**。第1〜3回を公開済み（2026-09-26）。決まったこと: 到達点は「一人で Git を使える」まで・**全10回**／練習用リポジトリは作らず、**この教材のリポジトリを受講者がフォークして**練習する。
> この文書の「3. 書き方の約束」を守って書く。

## 1. 何を教えるか

**Git だけを、一人で使えるところまで。** 黒い画面が初めての人が、自分の作業を Git で記録し、戻し、枝分かれさせ、コンフリクトを自分で直せるようになるまで。

外すもの（今の教材から消す）:

- Git と関係のない学習（プログラミング入門・AI との開発・性能・グラフ・API・DB・テスト・MCP・案件参画・学習計画）
- 教材の運営についての案内（`about.md`・目次の注意書き・`config.js` の該当設定）
- 逆算プランナー・参画の相談・参画準備のチェックリスト・練習用リポジトリ（`aq35/trainer-practice`）への案内

残すもの（仕組み）: sunao の画面とビルド・公開、1画面1操作の型、「うまくいきません」の3段構え、15分で声をかける、連絡先の設定。

## 2. ゴール（10回を終えたら、できること）

1. 変更を**意味のある単位で**コミットし、あとから**理由まで**たどれる
2. どのコマンドが**どこの何を消すか**分かったうえで、目的に合った取り消し方を選べる
3. ブランチで試し、マージし、**コンフリクトを自分で解決できる**
4. 自分のフォークにプッシュして、**GitHub 上で自分の履歴を確かめられる**

**確かめ方**: 第10回の最後に、自分のフォークの GitHub の画面で「コンフリクトを解決したマージコミット」が見えること。点数は付けない。

## 3. 書き方の約束（言葉・根拠・図）

### 3.1 言葉

**用語は Pro Git 日本語版にそろえる。** 教材の中で独自の呼び名を作らない。

| 英語 | 教材で使う言葉 | 根拠 |
| --- | --- | --- |
| working directory（working tree） | **作業ディレクトリ** | Pro Git 日本語版 1.3「三つの状態」 |
| staging area（index） | **ステージングエリア** | 同上（Git 本体の説明では index とも呼ぶ） |
| repository | **リポジトリ** | 同上 |
| committed / modified / staged | **コミット済・修正済・ステージ済** | 同上 |
| untracked | **追跡されていない** | Pro Git 日本語版 2.2 |
| commit | **コミット** | 同上 |
| branch / merge | **ブランチ／マージ** | Pro Git 日本語版 3 章 |
| conflict | **コンフリクト** | Pro Git 日本語版 3.2「マージ時のコンフリクト」 |
| fast-forward | **fast-forward**（訳さない） | Pro Git 日本語版も訳していない |
| HEAD | **HEAD**（いまいるブランチを指す、特別なポインタ） | Pro Git 日本語版 3.1 |
| fork / clone / push | **フォーク／クローン／プッシュ** | GitHub Docs 日本語版 |

- **初めて出てくるときは「正式な言葉＋やさしい言い換え」**、2回目からは正式な言葉だけを使う。
  例: 「**ステージングエリア**（次のコミットに入れるものを並べておく場所）」
- **使わない言葉**: 「作業フォルダ」「記録」（コミットの意味で）「3つの箱」「セーブポイント」。今の教材と図にある言い方は、書き直す。**ビルドで本文を検査し、見つけたら公開しない**（言い換えの表は `content/terms.js` に置く）。
- **たとえ話は、ずれる所まで書く。** たとえを使うときは「ここは違う」を同じ画面に書く。
- **言い切らない。** 「絶対」「必ず戻せる」「消えない」は、条件と根拠がそろうときだけ書く。
  例: ×「コミットしたものは消えません」→ ○「コミットしたものは、`git reflog` から見つけられることが多い（ただし期限がある）」＋根拠リンク
- **画面に出る英語は、実際の表示と一字一句同じにする。** 訳は横に添える。訳だけを書かない。

### 3.2 根拠

**コマンドの動きを書いた画面には、必ず根拠のリンクを付ける。** 画面の下に小さく「根拠: …」と出す。

根拠にしてよいもの（上ほど優先）:

1. **Git 本体**: `git help`、[Git リファレンス](https://git-scm.com/docs)、[Git のリリースノート](https://github.com/git/git/tree/master/Documentation/RelNotes)
2. **Pro Git 日本語版**（[git-scm.com/book/ja/v2](https://git-scm.com/book/ja/v2)）
3. **GitHub Docs 日本語版**（[docs.github.com/ja](https://docs.github.com/ja)）— フォーク・プッシュなど GitHub 側の操作
4. それ以外（ブログ・Q&A サイト・**AI の答え**）は根拠にしない。参考として紹介するのはよい

**画面に載せる出力は、実際に打って得たものだけ。**

- 各回の手順を**台本**（`content/runs/NN.sh`）にし、ビルドの前に使い捨てのフォルダで**本物の Git で実行して**出力を保存する（`tools/record.mjs`）。
- 教材には保存した出力を載せ、「**Git 2.43.0 で実行した出力**」と添える。手で書き写した出力は載せない。
- CI で毎回台本を実行し、**Git のバージョンで表示が変わったら知らせる**。

**ビルドで止めるもの**（1つでもあれば公開しない）:

| 検査 | 理由 |
| --- | --- |
| コマンドのある画面に、根拠リンクが無い | 言いっぱなしを防ぐ |
| コマンドの行数と「打つ前に」の説明の数が合わない／「いま何が起きたか」が無い | 意味の分からないものを打たせない |
| 画面に出す出力が、台本の実行結果と一致しない | 書き写し間違い・古い出力を防ぐ |
| 使わない言葉（3.1）が本文にある | 用語ゆれを防ぐ |

リンク切れは、ネットにつながる CI で週1回確かめる。

### 3.3 図（言葉で伝わりにくいこと）

**信頼できる順に使う。**

| 順 | 種類 | 使う場面 | 信頼できる理由 |
| --- | --- | --- | --- |
| 1 | **実行記録**（ターミナルの出力をそのまま） | コマンドを打った結果 | 本物の Git の出力。**文字のまま載せる**ので、コピー・検索・読み上げができる |
| 2 | **実行記録から機械で描いた図** | コミットの枝分かれ、3つの領域のどこが変わったか | 台本を実行した**あとのリポジトリの状態から**描く（`git log --graph` や `git status` の結果を図にする）。**図と出力が食い違わない** |
| 3 | 手描きの図 | 1・2で表せない考え方（なぜ分かれるのか、など） | 描いた図の下に、根拠のリンクを付ける |
| 4 | 画面写真（GitHub・VS Code） | ボタンの場所 | 見た目は変わるので、**撮った日付を入れる**。古くなったら撮り直す |

- **Pro Git の図は取り込まない。** Pro Git は CC BY-NC-SA 3.0 で、この教材（CC BY 4.0）とは条件が合わない。リンクで案内する。
- 色だけで意味を伝えない（差分は赤・緑に加えて `+` `−` を必ず見せる）。
- 図には説明文（読み上げ用）を必ず付ける。機械で描いた図は、**元になった出力を図のすぐ下に折りたたんで置く**。

### 3.4 AI で理解を深める

**事実は Git に聞く。意味は AI に聞く。答えは Git で確かめる。** 型は読み物 [Git を調べるコツ](../content/read/git-research.md)。

- 各回の完了画面に「**AI で深める**」を1問（多くは「自分の言葉で説明して、AI に直してもらう」形）
- 「うまくいきません」から AI に聞く文章に、`git status` の結果を貼る欄を付ける
- ★の回（わざと壊して戻す）では、打つ前に「何が変わる・何が消える・どう戻す」を AI に聞いてから打つ
- AI の答えは根拠にしない（3.2）。**確かめ方（`git help`・使い捨てフォルダ・空打ち）までを1セット**で教える

## 4. 練習の場所: この教材のリポジトリをフォークする

受講者は `aq35/trainer` を**自分のアカウントにフォーク**し、手元にクローンして練習する。**練習で触るのは `practice/` フォルダの中だけ**。

| 決めごと | 理由・根拠 |
| --- | --- |
| 練習は `practice/` の中だけ。ほかのファイルは触らない | 教材の本体を壊さない。第6回で「このリポジトリの本物の履歴」を読む題材にもなる |
| プッシュ先は**自分のフォークだけ**。本家にプルリクエストは出さない | 一人で使える範囲に閉じる。GitHub の「Contribute」ボタンは押さない |
| **フォークは公開される**ので、`practice/` に個人情報を書かない | 公開リポジトリのフォークは公開で、フォークだけの公開範囲は変えられない。フォークを消しても、中身が見られる状態で残ることがある（GitHub Docs「Forks」の Visibility of forks） |
| 本家の Actions はフォークでは動かさない | ワークフローに `if: github.repository == 'aq35/trainer'` を付ける（GitHub の既定の動きには頼らない。GitHub Docs に書かれているのは「公開リポジトリをフォークすると、**スケジュール実行の**ワークフローが既定で止まる」ことだけで、ほかのワークフローについては確かめられなかったため） |
| 回をまたいでも同じフォークを使い続ける | 第1回から第10回まで、**自分の履歴が1本につながる**。最後にそれを GitHub で見るのがゴール |

## 5. 構成（全10回）

各回 8〜12 画面、30〜60 分。★ は「わざと壊して戻す」画面がある回。

| # | 回 | できるようになること | 主なコマンド | 主な根拠 |
| --- | --- | --- | --- | --- |
| 1 | 道具をそろえる | ターミナルを開き、Git を入れ、名前とメールを設定し、GitHub のアカウントを作る | `git --version` `git config` | Pro Git 1.5・1.6 |
| 2 | フォークして手元に持ってくる | 教材をフォークし、クローンし、**この教材の本物の履歴**を眺める | `git clone` `git status` `git log --oneline` | GitHub Docs「リポジトリをフォークする」、Pro Git 2.1 |
| 3 | 最初のコミット | `practice/` にファイルを作り、コミットし、自分のフォークにプッシュして GitHub で見る | `add` `commit` `push` | Pro Git 2.2・2.5 |
| 4 | ステージングエリア ★ | 3つの領域の違いが説明でき、ステージから下ろせる | `status` `add` `restore --staged` | Pro Git 1.3・2.2・2.4 |
| 5 | 差分を読む | コミットする前に、何を変えたかを確かめる | `diff` `diff --staged` | Pro Git 2.2 |
| 6 | 履歴をたどる | いつ・誰が・なぜ変えたかを探す（題材はこの教材の本物の履歴） | `log` `show` `log -p` | Pro Git 2.3 |
| 7 | 取り消す ★ | 目的に合った取り消し方を選べる。消えるコマンドを見分けられる | `restore` `commit --amend` `revert` | Pro Git 2.4、リファレンス |
| 8 | 追跡しないもの | 追跡してはいけないものを外す | `.gitignore` `rm --cached` | Pro Git 2.2 |
| 9 | ブランチとマージ ★ | ブランチで試し、fast-forward とマージコミットの違いが分かる | `switch -c` `switch` `merge` `log --graph` | Pro Git 3.1・3.2 |
| 10 | コンフリクト ★（仕上げ） | コンフリクトを読み、選び、仕切り直せる。解決したマージをフォークにプッシュする | `merge` `merge --abort` | Pro Git 3.2「マージ時のコンフリクト」 |

**入れないもの**: `rebase`・`reset --hard`・`stash`・`reflog`・`cherry-pick`・プルリクエスト・チームでの運用。読み物「消えるコマンド・消えないコマンド」で**名前と危なさだけ**知らせる。

## 6. 読み物（寄り道・任意）

- **Git を調べるコツ**（書き済み。3.1〜3.3 に合わせて見直す）
- なぜ Git が生まれたのか（今のものを、3.1・3.2 に合わせて直す）
- 消えるコマンド・消えないコマンド（どのコマンドが、作業ディレクトリ・ステージングエリア・リポジトリのどこを消すか）
- コマンド早見表（逆引き）
- 用語集（3.1 の表から作る。Git の言葉だけ）
- ターミナル入門（今のものを流用）

## 8. 作る順番

1. 共通部品: 根拠リンクの表示・ビルドでの検査（3.2）・台本の実行と出力の保存（`tools/record.mjs`）・実行記録から描く図（3.3 の 2）・言い換え表
2. 古い教材を消す（運営の案内・Git 以外の回・プランナー）→ 第1〜3回を書く → **main に入れて公開**
3. 第4〜10回 → 読み物・用語集・コマンド練習 → 古い URL の転送

## 9. 決まったこと

- 画面写真（GitHub・VS Code）は載せず、公式の説明（写真つき）へのリンクで案内する
- 図は「実行した出力 → そこから描いた図 → 手描き → 写真」の順に信頼する（3.3）
- 最初の `git push` のサインインは、VS Code の中のターミナルで行う（VS Code の設定 `git.terminalAuthentication` が既定で有効で、中のターミナルの Git のサインインを VS Code が引き受けるため。Mac で Git Credential Manager などを別に入れずに済む）
